# Сверка и применение env на хосте: `sec diff` и `sec deploy`

Заметка о том, почему `deploy` устроен именно так. Список флагов — в
`sec deploy --help`.

## Зачем это появилось

Прод-конфиг `/app/.env.whois` правился руками: `ssh`, `sudo cp` для бэкапа,
`sudo sed -i`, дозапись строки. Попытка сделать то же «в лоб» через
`sec export whois --file whois:/app/.env.whois` сломала бы прод. Сверка на
живых данных (сравнивались только имена ключей):

| | ключей |
|---|---|
| стор `sec whois` | 22 |
| прод `/app/.env.whois` | 20 |
| общих | 13 |

В сторе лежали переменные CI и elastic-agent (`FLEET_*`, `OTEL_*`, `NPM_TOKEN`,
`YANDEX_CLOUD_REGISTRY_ID`), которым в `.env.whois` не место. На проде — семь
ключей, которых в сторе нет: `WHOIS_VERSION` патчит CI, `DOMAINATOR_DB_URL` и
`REDIS_URL` заведены только на хосте. `export` пересобирает файл целиком, то
есть снёс бы семь прод-ключей и дописал семь чужих.

Отсюда два вывода, на которых стоит вся фича: **сверка должна быть отдельной
read-only командой**, а **запись по умолчанию должна быть мержем**.

## Merge, а не replace

`deploy` обновляет только те ключи, которые есть в сторе. Ключи файла, которых
в сторе нет, не трогаются вовсе — как и порядок строк, комментарии, пустые
строки, отступы и префикс `export`. Реализация — `dotenv.Merge`: правит строку
на месте, недостающие ключи дописывает в конец.

Точечность важна не только ради чужих ключей. Если переписывать файл целиком,
каждый деплой даёт diff во весь файл, и глазами уже не увидеть, что реально
поменялось. Поэтому в `Merge` уходят **только** разошедшиеся и недостающие
ключи: совпадающие строки остаются байт в байт, даже если написаны непривычно
(`ODD  =  '  spaced  '`).

`--replace` возвращает поведение `export` — целиком из стора, с шапкой
«сгенерировано sec». Перед этим в diff видно, какие ключи хоста погибнут
(`- KEY  будет удалён`), и сколько их.

## Запись через `cat >` под sudo, а не tmp + mv

Прод-конфиг принадлежит root и читается демоном под его пользователем.
Классический атомарный приём (записать во временный файл рядом и переименовать)
сделал бы файл нашим: новый inode, наши права, наш владелец. Поэтому
`deploy` перезаписывает файл **на месте** — `sudo -n sh -c 'umask 077 && cat > путь'`.
Права 0600 навязываются только новому файлу (через `umask`), существующему —
никогда.

Расплата — запись не атомарна: обрыв связи на середине оставит обрезанный файл.
Страховка от этого — бэкап `<путь>.bak-<время>`, который снимается `cp -p`
**до** записи и выключается только явным `--no-backup`. Миллисекунды в имени не
для красоты: два деплоя в одну секунду перезаписали бы бэкап друг друга.

## sudo без пароля в чужом процессе

`sec` не спрашивает пароль sudo и не пропускает его через себя. Все команды
идут под `sudo -n` (неинтерактивный). Если хост отвечает «требуется пароль» и
мы в терминале, `sec` один раз запускает `ssh -t <host> sudo -v` — пароль
набирается на той стороне, в кэше credentials хоста, дальше `sudo -n` работает
минут пятнадцать. Без терминала (CI, пайп) — внятная ошибка и предложение
настроить NOPASSWD.

## Порядок шагов

1. собрать ключи проекта (файловые и бинарные отсеиваются: им в `.env` не место);
2. прочитать целевой файл (нет файла — не ошибка, создадим);
3. показать diff и спросить подтверждение (`--dry-run` / `--yes`);
4. бэкап;
5. запись;
6. **verify** — перечитать файл и сверить отпечатки записанных ключей;
7. `--after` — команда рестарта на хосте.

Verify стоит **до** `--after` намеренно: перезапускать сервис на файле, который
не сошёлся с отпечатками, нельзя — падение будет тихим и уже в проде. И
наоборот, без `--after` запись часто не применяется вовсе: `.env.whois`
подхватывается только на `docker compose up whois -d`, и на этом легко обжечься.

## `kind: config`

Отдельный вид значения рядом с `file` и `apikey` — несекретная настройка:
`WHOIS_LOOKUP_CACHE_MAX_SIZE=50000`, `WHOIS_HISTORY_PROVIDERS=whoxy`, URL
эндпоинта. Такие значения приезжают в стор вместе с остальным `.env` при
`import` и раньше портили жизнь дважды:

- `scan`/`redact` ловили их как утечку — любое значение из стора длиной ≥8
  символов считается секретом, и настройка совпадает в каждом втором файле
  проекта. Теперь `kind: config` из поиска исключён (`--include-config` вернёт),
  а сколько значений пропущено, видно в stderr;
- `diff`/`deploy` показывали их отпечатком, хотя понять «а что там сейчас
  стоит» можно только по значению. Теперь конфиг печатается открытым текстом:
  `~ WHOIS_HISTORY_PROVIDERS  различаются   стор: whoxy   файл: whoxy,ripe`.

Пометить: `sec meta <proj>/<KEY> --kind config` (или `--kind config` при
`set`/`gen`). В `ls -l` вид виден рядом с ключом.

## Острые углы, о которых стоит знать

**Метка `kind: config` разрешает печатать значение с обеих сторон.** В том числе
то, что лежит на хосте. Если ключ когда-то был обычным endpoint'ом, а на проде в
нём оказался DSN с паролем, `diff` покажет этот пароль открытым текстом. Метка —
утверждение о ключе, а не о конкретном значении, и проверить второе `sec` не
может. Не помечайте `config` ключи, в которых на хосте может оказаться секрет.

**Бэкапы копятся и содержат секреты открытым текстом.** Каждый деплой оставляет
рядом с конфигом полный `<путь>.bak-<время>` с правами оригинала. Ротации нет
намеренно — удалять чужие бэкапы опаснее, чем копить. Но каталог с ними не
должен попадать в docker build context (`COPY . .`) и под маску `.env*` в
раннерах; чистить — руками, когда деплой признан удачным.

**Вывод `--after` не фильтруется.** Команду пишет пользователь, её stdout/stderr
идут как есть — `--after 'docker compose config'` напечатает значения из только
что записанного файла. Это единственное место, где `sec` может показать секрет
не по своей воле.

**«Нечего делать» не выполняет `--after`.** Рестарт — следствие записи; если
записи не было, сервис не трогается (иначе деплой по расписанию перезапускал бы
его вечно). `sec` об этом говорит отдельной строкой в stderr — если предыдущий
`--after` упал, рестарт надо повторить руками.

**Гонка с CI.** Файл перечитывается непосредственно перед записью и сверяется с
тем снимком, по которому строился diff: если между показом diff и подтверждением
кто-то поменял файл, `deploy` откажется писать. Полной блокировки нет — окно
между этой сверкой и самой записью остаётся.

## Что осталось за бортом

- Многострочные значения в env-файле: `dotenv` их не поддерживает намеренно, и
  `Merge` работает построчно. `deploy` такой файл **не** трогает (отказывается с
  перечислением ключей), `diff` предупреждает. Сертификат в `.env` не кладут —
  для этого есть `kind: file` и `run --file` / `get --out`.
- Права и владелец нового файла: создаётся под 0600 от имени того, кто пишет
  (root при `--sudo`). Если демону нужен другой владелец — выставить один раз
  руками, дальше `deploy` его сохранит.
- `--sudo` для локального файла на Windows: там нет ни `sudo`, ни `sh` — `sec`
  скажет об этом прямо. Удалённый `--sudo` с Windows работает (весь sudo живёт
  на той стороне ssh).

# Skill: sec

Секреты в XChaCha20-Poly1305-файле, мастер-ключ — в системном хранилище ОС.
Отдельный CLI, ставится брю: `brew install kaidstor/tap/sec`. Исходники —
github.com/kaidstor/sec (это **не** rebrandy-проект: задачи в FB не заводить).

**Список команд — `sec --help`, флаги конкретной команды — `sec <cmd> --help`.**
Здесь только то, чего в `--help` нет: политика для агента и гочи.

## Адресация

Секрет = `<proj>/<KEY>`. Без проекта берётся имя текущей директории, поэтому
внутри папки сервиса достаточно `sec run -- just dev`.

Третья ось — профили: один сервис, несколько наборов значений (стенды,
компании). Профиль — часть адреса, как версия в npm: `bot@commercial/TOKEN`,
`sec run bot@max -- …`. Без `@` подставляется дефолт из `.sec`; явная форма
`bot@` — базовый набор в обход дефолта. Набор профилей (`profiles:`) и дефолт
(`default:`) объявляются в файле `.sec` в папке сервиса — его читают и CLI, и
агент. Там же список обязательных ключей для `sec check`.

## Машинный вывод

- Когда ответ надо разобрать, а не прочитать глазами, — `--json` на любой
  команде: конверт `{v, command, exit, data, warning, error{kind, message}}`
  в stdout, отказ тоже в stdout (stderr пуст). Коды выхода и `kind` — в
  `sec --help`.
- **`get --json` кладёт значение в `data.value`** — это тот же показ
  значения, правило 1 политики действует. Проверить, не раскрывая, —
  `get --peek --json` или `--fingerprint --json`.
- Голый `sec get <ref>` печатает только значение: так его читают обёртки
  (`$(sec get …)`, `token_ref` в конфигах CLI). `--json` туда не дописывать.
- Гейты `check`, `diff`, `stale` выходят с кодом 2 и тогда, когда всё
  отработало, но не сходится: отличать от ошибки по `error: null`, причина —
  в `data`.
- `run --json` отказывает: stdout `run` принадлежит запущенной команде, а
  `--json` после `--` уходит ей как есть.

## Политика для агента

1. **Значения секретов в чат не выводить.** `get` без `--clip`/`--peek`/
   `--fingerprint` — только по явной просьбе показать значение.
2. **Заведение секрета — так, чтобы значение не прошло через чат и argv.**
   Пользователь копирует в буфер → `sec set <proj>/<KEY> --clipboard --clear`;
   либо он сам вводит скрытым вводом; либо значение генерируется (`sec gen`) и
   агент его не видит. Значение с диска — пайпом, не аргументом.
   **Несекретные настройки (`kind: config` — хост, порт, логин, endpoint) агент
   заводит сам**, правило про буфер не про них: набор ключей — одним
   `sec import <proj> -` через пайп (или `sec import <proj> <path>/.env`, если
   конфиг уже лежит файлом), одиночный — `printf … | sec set`. После импорта
   пометить `--kind config`: `import` тип не проставляет, а непомеченная
   настройка потом шумит в `scan`. Значение, которому место ссылкой на чужую
   пачку, через `import` не проводить — только `sec link`.
3. **Перед заведением — `sec find <KEY>`.** Такой ключ может уже лежать в другой
   пачке: тогда `sec link` (живая ссылка), а не копия. Общий источник правды не
   расходится, копии расходятся.
4. **Искать фильтром, а не глазами.** `sec find <шаблон>` по всему хранилищу,
   `sec ls <proj> --filter <шаблон>` внутри пачки. Не выгребать `sec ls --json`
   целиком, чтобы искать в выводе.
5. **Перед коммитом — `sec scan --staged`.** Перед показом лога или вывода
   команды, где мог засветиться секрет, — `<cmd> 2>&1 | sec redact`.
6. **Реорганизация — `sec mv`/`sec link`, а не `get`+`set`:** не раскрывает
   значение и сохраняет историю. Перед `rm ... --all` — подтверждение.
7. Если пользователь прислал значение открытым текстом в чат — сохранить можно,
   но предупредить, что оно засвечено, и предложить ротацию.

## Гочи

- **`run`/`export` не инжектят ключи `kind: file` в env** — многокилобайтный PEM
  в окружении каждого дочернего процесса упирается в ARG_MAX. Нужен путь к файлу
  на время команды — `sec run --file`; нужно именно содержимое в переменной —
  явный `--only <KEY>` или `--include-files`.
- **`--file` перекрывает одноимённый env-ключ**: если в пачке есть `KEY` и в том
  же запуске указан `--file KEY=...`, в окружение уйдёт путь к файлу, а не
  значение из стора (CLI предупредит в stderr).
- **`scan` и `redact` игнорируют значения короче 8 символов** (иначе совпадало бы
  в каждом втором файле). Счётчик пропущенных — в stderr, порог — `--min N`.
  Оба видят только значения из стора: это не универсальный DLP.
- **`import` строкой (`sec import proj '{"KEY":"…"}'`) светит значение в argv и
  истории shell.** Агенту — только пайп, файл или `--clipboard`.
- **Значение по `link`/`extend` read-only в потомке**: `set`/`gen`/`undo`/`import`
  откажутся. Менять — у родителя, оторвать — `sec unlink`, перекрыть своим —
  `sec set --override`.
- **`export` пишет только в файл**, в stdout — принципиально нет.
- **Прод-конфиг на хосте обновлять `sec deploy`, а не `export --file host:/path`.**
  `export` пересобирает файл целиком и снесёт ключи, которых в сторе нет (их
  патчит CI или админ руками) — на реальном whois это было бы 7 ключей из 20.
  `deploy` по умолчанию **мержит**: трогает только ключи стора, порядок строк и
  комментарии оставляет как есть. `--replace` возвращает поведение `export` и
  сообщает, сколько ключей хоста при этом потеряется.
- **`sec diff <proj> <host>:/путь` — сверка до всякой записи** (только чтение,
  значения не раскрываются). Начинать с неё: расхождение стора и прода видно
  одной командой.
- **`deploy` не перезапускает сервис.** `.env` подхватывается не на лету:
  без `--after '<команда рестарта>'` файл новый, а процесс со старыми
  значениями — и это молча. У whois рестарт — `cd /app && docker compose up whois -d`.
- **`--sudo` нужен для root-овых конфигов** (все прод-`.env` такие). Пароль sudo
  вводится в ssh-сессии на той стороне, через `sec` не проходит; на хосте без
  NOPASSWD первый вызов попросит ввести его руками.
- **`kind: config` — не секрет, а настройка** (endpoint, список провайдеров,
  размер кэша). `scan`/`redact` такие значения не ищут (вернуть в поиск —
  `--include-config`), `diff`/`deploy` показывают их открытым текстом. Помечать
  `sec meta <proj>/<KEY> --kind config` — иначе настройка, приехавшая из
  `import`, шумит в `scan` на каждом втором файле проекта. Обратная сторона:
  метка разрешает печатать и то значение, что лежит **в файле на хосте** —
  не помечать так ключ, в котором на проде может оказаться секрет.
- **`deploy` отказывается править файл с многострочными значениями** (кавычка
  открыта, а закрыта строкой ниже): построчный merge порвал бы такое значение
  пополам. Такой конфиг править руками.
- **Бэкапы `<путь>.bak-<время>` копятся на хосте и содержат секреты открытым
  текстом.** Ротации нет: чистить руками, следить, чтобы каталог не попадал в
  docker build context и под маску `.env*` у раннеров.
- **`forget` необратим** — чистит историю и redo, `undo` уже не вернёт. Делать
  только после того, как новое значение проверено рабочим.
- **На Linux** мастер-ключ идёт в libsecret, если он поднят; иначе файл
  `~/.config/sec/key` или `SEC_KEY`. На headless-сервере штатный путь — `SEC_KEY`.
- **`set` со скрытым вводом требует TTY** — в headless подавать значение пайпом.
- **`sec log` и `sec stats` — про разное.** `log` это журнал обращений: кто и к
  какому ключу шёл; хранит год (по 1 МБ в датированные архивы), но по умолчанию
  читает только текущий файл — за архивы отвечает `sec log --all`. `stats` —
  счётчики за всё время: чем из CLI пользуются, а что заведено впустую; имён
  проектов и ключей там нет вовсе.

## Доступ к серверу ссылок для другого человека

Сервер — `share.kaidstor.ru`, хост `my-vpn`, контейнер `sec-share`. Токен
создателя выпускается только на хосте: HTTP-эндпоинта и регистрации нет.
Свой токен передавать не нужно и нечем — пара «адрес + токен» лежит в служебном
проекте `_share`, чьё имя намеренно не проходит валидацию, поэтому `get`, `cp`,
`meta` по нему отказывают. На каждого человека выпускается именной токен: он
отзывается отдельно и видит только свои ссылки.

```bash
ssh my-vpn docker exec sec-share sec-share token ls          # кому уже выдано
ssh my-vpn docker exec sec-share sec-share token add <имя> \
  | sec set sec-share/TOKEN_<ИМЯ>                            # выпуск сразу в стор
sec meta sec-share/TOKEN_<ИМЯ> --kind apikey --note 'выпущен для …; отозвать: token rm <имя>'
sec share sec-share/TOKEN_<ИМЯ>                              # одноразовая ссылка человеку
```

Получателю кроме ссылки нужен адрес — подключается он одной командой
`sec share setup https://share.kaidstor.ru`, токен вводится скрытым вводом.
Отзыв: `ssh my-vpn docker exec sec-share sec-share token rm <имя>`.

- **`token add` печатает значение ровно один раз** (в `tokens.json` остаётся
  только sha256), пояснение при этом уходит в stderr и пайпу не мешает. Гнать
  вывод прямо в `sec set` — так значение не проходит ни через чат, ни через argv,
  ни через промежуточный файл; `set` со stdin сам режет хвостовой `\r\n`.
- **Копия в сторе — не дубль, а страховка:** одноразовая ссылка сгорает по TTL,
  даже если её не открыли, и без копии пришлось бы выпускать токен заново
  (старый к тому моменту уже никому не известен). С копией — повторный `sec share`.
- **Подсказка про дубль после `sec set sec-share/URL` ведёт в тупик:** `sec` предлагает
  `sec link sec-share/URL _share/URL --force`, а эта команда падает на валидации
  имени `_share`. Держать адрес обычным ключом с `--kind config`.
- **`sec scan` ругается на любой файл с адресом сервера.** Значение `_share/URL`
  пометить `kind: config` нельзя (та же валидация имени), поэтому скан видит
  `share.kaidstor.ru` как секрет в открытом виде — в этом файле, в `docs/share.md`,
  в `server/compose.yml`. Находка на `_share/URL` — шум, а не утечка.

## Куда смотреть, когда

| Задача | Команда |
|---|---|
| выдать человеку доступ к серверу ссылок | `… token add <имя>` → `sec set` → `sec share` (см. раздел выше) |
| запустить с env проекта | `sec run [proj] [--only A,B] -- cmd` |
| файловый секрет на время команды | `sec run --file [ENV=]<KEY>[:путь] -- cmd` |
| собрать `.env` | `sec export [proj] --file .env` |
| что разошлось с прод-конфигом | `sec diff <proj> <host>:/путь --sudo` |
| применить стор на хост | `sec deploy <proj> --to <host>:/путь --sudo --after '<рестарт>'` |
| сверить значение, не раскрывая | `sec get --peek` / `--fingerprint` / `sec verify` |
| мигрировать существующий `.env`/JSON | `sec import [proj] <path\|->` |
| 2FA-код (печатать в чат безопасно) | `sec otp <proj>/<KEY>` |
| передать секрет человеку | `sec share <proj>/<KEY>` (URL печатать можно) |
| передать пак целиком | `sec share <proj> --all` или `--only A,B` (получатель скачает `.env`) |
| что пора ротировать / здоровье стора | `sec stale`, `sec doctor` |
| кто трогал секреты | `sec log [proj[/KEY]]` |
| что из CLI используется, а что мертво | `sec stats [--days 14]` |
